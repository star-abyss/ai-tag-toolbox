# 一、执行摘要

## 1.1 这一层是什么

**它是"这个 AI 是什么"与"这些话怎么说出口"的定义与装配。**

它不提供能力（能力在七个模块里），它提供的是：

| 它决定 | 落到哪 |
|---|---|
| 这次让模型看见哪些工具 | 预设里的工具表 → 注册进 DSH 的工具注册表 |
| 这次对模型说什么 | 世界书请求启用列表 → 命中条目 → 系统提示词段 |
| 这次挂哪些知识 | 世界书模块保存各请求启用列表，并挑出带落点的条目 |
| 这次走哪条 API | 路由表 → 逐次调用带上的 `provider` |
| 什么时候停下来问用户 | 计划模式 |

## 1.2 一句话

> **一份设置 = 模型配置 + 业务工具启用、说明与顺序偏好。提示词正文统一使用世界书。**
> **默认那份我们给，用户爱咋改咋改；改坏了拿原件盖回去。**

## 1.3 三条定性

| # | 定性 | 在这一层的体现 |
|---|---|---|
| 1 | **彻（彻）底放开** | 用户预设的字段不校验、不补全、不警告。缺了就是缺功能，写错了就是调用失败 |
| 2 | **不做安全边界** | 本层不含任何能落到系统上的动作（无 shell、无任意路径读写、无网络出口），因此沙箱与审批一条不加 |
| 3 | **缺省是缺省，错是错** | "没写"跟随主 AI；"写了但指向不存在"明确失败。不做多级回落 |

# 二、目标与非目标

## 2.1 目标

| # | 目标 | 判据（可验） |
|---|---|---|
| G1 | 用户能改"这个 AI 是谁、按什么流程办事" | 改一段文本，下一次请求的系统提示词随之改变 |
| G2 | 用户能改"模型能用哪些工具、参数长什么样" | 改工具表，模型的工具 schema 随之改变 |
| G3 | 同一台机器上多套"AI"并存、可切换 | 预设可新建 / 复制 / 导入 / 改名 / 删 / 恢复默认 |
| G4 | 每个请求能走各自独立的 API 配置 | 识图走本地、翻译走官方，可同时成立 |
| G5 | 关掉工具表即退化为纯对话（"当酒馆用"） | 工具表清空后，模型收不到任何工具 schema，对话仍成立 |
| G6 | 默认那份开箱能跑 | 默认的工具表与模块声明逐字一致；默认流程提到的工具都在表里 |

## 2.2 非目标（明确不做）

| 不做 | 为什么 |
|---|---|
| 酒馆的角色卡 / 正则 / 扩展脚本 / 表情 / 群聊 | 不在本轮范围；各有各的归属 |
| 酒馆的采样参数（温度 / 惩罚 / 上下文 / `wrap_in_quotes` 等） | 归 DSH 的 provider，我们不存第二份 |
| `atDepth` 的任意深度注入 | DSH 的历史是持久日志，没有"往中间插"的能力（§8.4） |
| 多级回落、兼容层、回退开关 | 要回退用 git |
| 任何形式的沙箱 / 审批 / 路径校验 | 本层没有能越界的手段（§1.3 第 2 条） |
| 界面（本轮） | UI 适配程序，不是程序适配 UI |

# 三、术语

| 词 | 意思 |
|---|---|
| **DSH** | DeepSeek Harness，本层跑在其上的运行时 |
| **请求** | 一件"要对模型说的事"的名字：`主AI` / `翻译` / `识图` / `文生图`。**由请求表定义** |
| **预设** | 一份具名配置：身份 + 流程 + 工具表 + 世界书引用 + 模型 |
| **段** | 预设里的一条：`{ 名字, 正文, 启用, 角色?, 顺序 }` |
| **工具表** | 预设里的一串条目：`{ 名字, 说明, 参数, 动作, 开关 }`。**注册工具的唯一来源** |
| **注册表** | 工具表的另一面：由工具表算出来的、给模型看的那份目录。**不单独存** |
| **API 池** | 用户配的多套 API 连接：`{ 名字 → 地址, 凭据引用, 模型候选 }` |
| **路由表** | `{ 请求名 → API 池里的哪一条 + 哪个模型 }`。空 = 跟随主 AI |
| **世界书** | 一批"按条件进出的正文"。住世界书模块，本层只引用 |
| **落点** | 一条世界书条目要放在哪：`前` / `后` / `按深度` |
| **默认预设** | 随程序走、用户不可改的那一份（无写路径） |
| **草稿 / 存档** | 同模块层：改作用在草稿上，落下要按保存 |

# 四、系统上下文与分层

## 4.1 三层（沿用项目结构，标注本层落点）

```
① 模块层   七个模块，互不认识，也不认识模型与 DSH
              ↓ 被使用（不是被包裹）
② 门面层   本层。模型与界面都只跟这一层打交道
              · 请求表 · API 池与路由 · 提示词装配 · 工具注册
              · 一个"工具"可以用多个模块
              ↓ 由谁执行
③ 执行层   那一段顺序：归一化参数 → 向模块要东西 → 调模块 → 整形结果
```

**本层的全部落点是 ② 与 ③**，写在 DSH 的一个 Host 插件里（下文称"对接层"）。

## 4.2 运行时（DSH）提供什么、我们提供什么

| 能力 | 谁提供 | 我们的用法 |
|---|---|---|
| Agent 循环（多步 · 工具 · 取消 · 流式 · 重试） | **DSH** | 直接用，不重写 |
| 会话与持久日志 | **DSH** | 直接用；历史是只追加日志，模型可见即已记录 |
| 工具注册表与调用流水线 | **DSH** | 把工具表登记进去 |
| 系统提示词注册表与组装 | **DSH** | 注册我们的段；读组装结果用于显示 |
| 模型调用（HTTP · 凭证 · 流式 · provider 路由） | **DSH** | 逐次调用带 `provider` / `model` |
| 人设（persona）槽位 | **DSH** | 用 order 0 那个位置放身份 |
| **身份 / 流程 / 工具表 / 世界书 / 路由** | **本层** | 本文档的全部内容 |
| **七个能力模块的能力** | 模块层 | 由对接层包成工具 |

**边界**：DSH 的装配方式（profile + patch 层）我们不改；我们把本层做成**自己的装配代码**，只借用它的库与服务（见 §13.2）。

## 5.5 请求是怎么拼出来的（本层的插手点）

`dsh-agent-loop/lib/index.js` 的 `preStep`（行号为本机发行包，仅供定位）：

```
:906  claim()              本步批次的消息被领走（并发出 agent/inbox/claimed）
:907  assemble()           组装系统提示词与工具 schema   ← provider 在这里被调用
:909  renderContextSections() / runtimeContext.project()   运行时事实
:911  agent/pre-step 瀑布   可增删本步消息
:1056 system/message 落盘
:1061 user/message 落盘
```

**由此得到两条对本层关键的性质**：

- **P1 · 组装早于消息落盘**：组装那一刻，**本步的新用户消息还没进会话**；`agent.session.deriveMessages()` 拿到的是**上一步之前**的历史。
- **P2 · `agent/inbox/claimed` 早于组装**（`claim()` 在 `:103` 发出，组装在 `:907`）：**世界书命中所需的"本轮文本"从那里拿，时序正好。**

**外部插手的全部位置**（本层只用到前三个）：

| # | 位置 | 能干什么 |
|---|---|---|
| 1 | `system-prompt/assemble` 瀑布 | 读整份组装（段 / 上下文 / 工具 / 变量），可改完返回 |
| 2 | 段 provider | 每步现算一段文本（同步，可读 `agent.session`） |
| 3 | `agent/inbox/claimed` | 拿到本步批次（用于命中扫描） |
| 4 | `agent/pre-step` 瀑布 | 增删 / 替换本步消息 |
| 5 | `agent/request` 瀑布 | 换这次调用的配置（provider / model / 温度 / 输出上限） |
| 6 | 收件箱 `inject` / `steer` / `followup` | 往下一步或下一轮投消息（落点只能在末尾） |

# 六、请求表

## 6.1 形状

```js
const 请求表 = {
  主AI:   { 说明: '和用户聊天 / 干活' },
  翻译:   { 说明: '把一段文本按词翻成中文' },
  识图:   { 说明: '看一张图，出标签与描述' },
  文生图: { 说明: '把想法整理成一份出图用的提示词' },
};
```

## 6.2 一表三用

| 用途 | 谁读 |
|---|---|
| 界面上列出"有哪些请求"、各自配哪条 API | 设置页 |
| 路由表与启用列表以请求名为键 | 本层 |
| 回执里的 `请求` 叫什么 | 调用方原路发回去 |

**三处读的是同一张表，不另存第二份。** 加一种请求 = 加一行。

## 6.3 为什么它是常量而不是配置

**因为它就是那份定义本身。** 用户能改的是**它们各自的行为**（走哪条 API、挂哪些书、用哪套预设），那些在 §七 与 §八。

# 七、API 池与路由

## 7.1 三样东西三个家

```
① API 池     地址 · 凭据引用 · 模型候选        ← 配置，一条一行
② 路由表     哪个请求走池里的哪一条 + 哪个模型   ← 引用
③ 预设       用哪个模型、什么参数              ← 预设里那两格
```

| 规矩 | 理由 |
|---|---|
| 池里存**凭据引用名**，不存密钥 | 密钥两个地方各存一份 = 换 key 要改两处。密钥住 DSH 的凭据存储 |
| 路由里存**池条目的名字**，不存地址 | 地址改了不用动路由表 |
| 预设里存 **model 名**，不存 provider | 换 provider 不用动预设 |

## 7.2 数据形状

```jsonc
{
  "池": {
    "本地":     { "适配器": "pi-ai", "地址": "http://127.0.0.1:1234/v1", "凭据": "本地_KEY", "模型": ["qwen-vl"] },
    "官方":     { "适配器": "deepseek", "凭据": "DEEPSEEK_API_KEY", "模型": ["deepseek-flash"] },
    "我的网关":  { "适配器": "pi-ai", "地址": "https://…", "协议": "anthropic", "凭据": "MY_GW_KEY", "模型": ["…"] }
  },
  "路由": {
    "主AI":   { "走": "官方", "模型": "deepseek-flash" },
    "识图":   { "走": "本地", "模型": "qwen-vl" },
    "翻译":   {},
    "文生图": { "走": "我的网关", "模型": "…" }
  }
}
```

## 7.3 缺省与错（**本层唯一的 `||`，且它兜的是"这一格空着"**）

```js
const 路由 = 路由表[请求];
const provider = 路由?.走   || 主AI那条;      // 没写 → 跟随主 AI
const model    = 路由?.模型 || 主AI那个模型;
await ctx.llm.stream({ provider, model, messages, … });
```

| 情形 | 处理 |
|---|---|
| 路由表那一行**没写** | **跟随主 AI** |
| 写了，但池里没这一条 | **失败**（找不到路由），**不回落** |
| 凭据引用解析为空 | 失败（`MISSING_CREDENTIAL`） |
| 密钥不对 / 地址不通 / 模型不存在 | 提供方报错，原样归类交回 |

**为什么"没写"和"写错"必须分开**：混在一起，一个拼错的名字会让识图静悄悄地走错链路而无人知晓。

## 7.4 落点：调度那一小块

```
请求({ 请求, system, user, 图片?, 信号? })
  ① 查路由（§7.3 两行）
  ② ctx.llm.stream({ provider, model, messages, signal })
  ③ 失败 → 归成中文可分辨的码；重试的规矩读 provider 的配置
  ④ 交回 { 正文, 用量, 试了几次, 用的谁: { provider, model } }
```

**回执带 `用的谁`**：用户随时看得出这张图到底发去本地了没有（判据②）。

## 7.5 provider 列表不由我们管（本节的例外）

**DSH 自己也有"配了哪些 API"这一面**（provider 注册、凭据存储、设置页）。若用户已在 DSH 那边配好，我们的池只需要**引用**它——**不复制一份地址和密钥**。两种形态都支持：

| 形态 | 池条目 |
|---|---|
| 引用 DSH 已注册的路由 | 只写路由名 |
| 自己声明一条网关 | 写地址 + 凭据引用 + 模型候选（由对接层注册成路由） |

# 八、系统提示词

## 8.1 最终形状（一条 system 消息，按 order 拼）

| order | 内容 | 来源 |
|---:|---|---|
| **500** | 计划模式规则（激活时才出文本） | DSH 的 plan-mode，正文来自我们的配置（§9） |
| **5110 / 5120** | 世界书《前》《后》的命中条目，包含主 AI 身份与工作方式 | 世界书模块 |

> 世界书按落点分堆；同一落点内保留启用书顺序和书内条目顺序。身份与工作方式是普通常驻条目，不另加隐藏正文。

## 8.2 第二条消息：每轮追加的运行时内容

```
[system]  计划模式（宿主提供时）+ 世界书前后
[user]    ← 本轮命中、落点是《按深度》的条目
[user]    用户这次的话
[assistant] / [tool] …（循环继续）
```

**为什么走这里而不是系统提示词**：DSH 的系统提示词是**一个节点**，往里塞随话题变的内容会让它每轮都变；而"每轮追加一条 user 消息"是 DSH 自己就在用的做法（运行时事实、AGENTS.md、技能目录都这么投）。

**落点语义（本层的取舍）**：

| 世界书的落点 | 本层落在哪 |
|---|---|
| `前` | 系统提示词内的世界书前段 |
| `后` | 系统提示词内，`前` 之后 |
| `按深度` | **每轮追加的那条 user 消息（紧贴输入之前）** |

**`按深度` 的边界如实记**：酒馆能插到"距末尾第 N 条"，本层**只能落在最浅那一档**（N=0，紧贴输入之前）。`深度` 字段原样保留、原样带出去，**导出往返语义不变**；界面上如实写"这条按深度落，本次落在输入之前"。

## 8.3 一次请求里，提示词与工具的稳定性

| 事实 | 后果 |
|---|---|
| 段 provider 每步都会被调用，但**重试不重算** | 一次用户回合里多次工具调用会多次组装；**本层让轮内结果保持稳定**（§8.5） |
| 同一请求序列内提示词变化，若路由声明 `in-history`，新提示词**追加到历史之后** | **系统提示词每轮都变 ⇒ 历史里每轮多一条全文系统提示词**。这是 §8.5 那条纪律的由来 |
| 渲染结果为空的处理 | 所有系统节点被清空 ⇒ **"什么都不启用"是合法状态**，不是坏配置 |

## 8.4 什么不该写进系统提示词

| 不写 | 归谁 |
|---|---|
| 工具怎么用、什么时候用 | **工具 schema 自带**（`description` / `parameters`）；"什么时候用"属于流程，属于预设 |
| 库里有什么、数据长什么样 | **能查**：调一次工具就知道。**写进提示词会与真实值漂移** |
| 这台机器什么系统、连的哪台 ComfyUI | 本层的 AI 没有能用到它的手段 |
| 用户是谁、说什么语言 | 用户自己的话会说 |
| 每轮都在变的事实（时间等） | 写进去等于让系统提示词每轮都变。要写就写在 10200 那个位置，并接受代价 |

## 8.5 两条硬纪律

| # | 纪律 | 由来 |
|---|---|---|
| 1 | **轮内世界书命中结果稳定**（一轮里多次工具调用，命中集合不变） | 避免 `in-history` 追加把历史撑爆；也符合"一次回答 = 一次刷新"的直觉 |
| 2 | **世界书命中扫描发生在组装之前**（挂 `agent/inbox/claimed` 记住本步批次，provider 组装时读它） | 组装那一刻本步消息尚未落盘（P1），而该事件早于组装（P2） |

# 九、计划模式

## 9.1 它是什么

DSH 提供的一个**会话状态**：开着的时候，系统提示词 order 500 处多一段文本；一个出口工具（`exit_plan_mode`）把方案交上来，**弹窗请你批准**。批准则下一轮动手，不批准则把反馈交回模型，它改完再弹。

**它的机制与配置面的分工**：

| 部分 | 归谁 |
|---|---|
| 状态、进入 / 离开、评审弹窗、出口工具 | **DSH**（`dsh-plan-mode`） |
| **那段正文** | **我们**（配置项 `section`） |

DSH 自带的默认正文是"软件规划"那套（先探索仓库、别动文件、交出实现计划）。**我们可以整段换成自己的循环。**

## 9.2 本层的用法：把"评估—返工"做成闸门

**用途**：需要"先给方案让我看"或"做完先问我满不满意"的场合，典型是**生图后看是否满意、不满意再来一轮**。

**正文内容（我们的默认预设里的那一份）**，要点：

1. 先给出**要做什么**的一句话方案，等批准
2. 批准后才动手
3. 产出后**主动问是否满意**
4. 不满意 → 只改被指出的部分，再来一轮
5. 不要在没有批准的情况下连做好几轮

## 9.3 如实记的两条

| 事实 | 影响 |
|---|---|
| 它**只约束文本，不限制工具**（DSH 官方说明："需要强制限制的部署要分别配置沙箱与审批"） | 本层没有需要强制的动作，这条不影响我们 |
| 进出会改变系统提示词（从 order 500 起） | 与 §8.5 同一条代价，可接受：进出是低频动作 |
| 出口工具与弹窗文案是 DSH 的口气（`Approve this plan and leave plan mode?`） | **不改名**（改名要动宿主）。功能就是"要不要过" |

# 十、主 AI 的模型与工具设置

## 10.1 数据与默认

主 AI 模块保存具名设置和请求选择；每份设置只包含 `name`、`tools`、`toolsOrder`、`model`。`执行` 返回当前设置标识、业务工具表与模型。身份、流程和世界书引用不属于设置。

工具 schema 从装配层的单份绘画业务定义实时生成；用户设置只保存停用、参数说明与顺序偏好。默认设置只读，复制后可编辑模型与工具。提示词正文另在世界书中编辑，启停世界书无需复制设置。

## 10.2 设置与世界书分别生效

设置切换只影响模型和工具。各请求通过世界书 `书({动作:换,请求,启用})` 保存自己的启用列表；执行与预览统一调用 `执行({请求,文本})`，不传设置里的书籍覆盖列表。世界书正文只存世界书模块一处。

## 10.3 拼装与动态信息

装配层把命中按落点装入系统消息或按深度追加内容，另外生成会话格式和当前素材信息；工具定义单独作为 tools 发送。程序动态信息在界面可查看，不作为可编辑世界书正文重复存储。

## 10.4 用户存档

旧用户文件保留，不迁移正文或引用。读取仅消费现行配置字段，主动保存后只写现行设置；没有旧正文兜底。默认身份和流程的原文逐字存入主 AI 默认世界书。

# 十一、世界书在上层的位置

## 11.1 定位

**它是一批"按条件进出的正文"，谁的请求都能挂。** 主 AI 只是它的一个使用者。

| 它答什么 | 本层拿来干什么 |
|---|---|
| 这次启用了哪几本 | 界面上说出"用了哪几本" |
| 每本里哪些条目命中 | 拼进提示词 |
| 每个条目放在哪 | 按落点分堆（§8.2） |

## 11.2 两种条目 = 两种用法

| 条件 | 效果 | 典型用途 |
|---|---|---|
| `always`（恒常） | 每轮都在 | 角色设定、总则 |
| `keys`（关键词命中） | **提到才想起来** | 名词解释、设定细节 |

## 11.3 四个请求的默认世界书

主 AI、文生图、翻译、识图分别默认启用自己的基础书；对应关系只定义在装配层 `模块清单.js` 的默认启用映射里。主 AI 默认书包含身份和工作方式两条常驻条目，使用同一套启停、关键词、落点、复制与导入导出能力。

世界书模块只在请求没有存档记录时使用注入默认；显式空列表持续停用，刷新和重启不重新启用。主 AI 不保留独立身份、流程分段，也不通过设置的书籍引用覆盖订阅。

用户书 scope 与默认映射界定请求归属。书表、启用和执行共同遵循归属；新建、复制、导入不自动启用。详见《主AI提示词统一.md》。
## 11.4 本层的"默认不出错"判据（给我们的，不是给用户的）

| 判据 | 怎么验 |
|---|---|
| 默认工具表的参数与业务声明**逐字相同** | 自检里对一遍（模型工具来自绘画业务定义） |
| 默认工具名**全部合法**（`^[a-zA-Z0-9_-]+$`） | 自检里对一遍（决定 43）；名字不合法会被提供方 400 打回 |
| 默认流程里提到的工具**都在表里** | 自检里对一遍 |
| 用默认那份能跑完一轮 | 一次真机联调（§16.3） |

**除此之外一条校验都不加。**

# 十三、失败与装配

## 13.1 失败一律可分辨

| 失败 | 表现 |
|---|---|
| 模块的动作失败 | `{ ok:false, reason, code }`（模块层信封），对接层**抛出去**，模型看到一条错误结果 |
| 工具表指向不存在的动作 | 同上：调用失败，**错交回给 AI** |
| 路由指向不存在的池条目 | 失败（找不到路由），**不回落** |
| 凭据缺失 / 无效 | `MISSING_CREDENTIAL` / 提供方 401 |
| 提示词组装失败（未知变量等） | DSH 抛错；**我们不在 provider 里制造这类失败**（默认那段文本不引用未注册的变量） |

**一条贯穿**：**失败不需要我们发明新的表现**——模块给码与理由，DSH 给错误结果，模型看得到，用户查得着。

## 13.2 装配（对接层）

**形态**：一个 Host 插件包，自成一个目录，与七个模块平级，**不塞进任何模块目录**。

**它做四件事**：

| # | 做什么 |
|---|---|
| 1 | 按配置装模块（路径从配置来；**参数里永远不出现地址 / 路径**） |
| 2 | 按预设的工具表登记工具（`ctx.tools.register`） |
| 3 | 注册提示词段：世界书前（5110）· 世界书后（5120）；计划模式仍由宿主配置 |
| 4 | 挂 §5.5 的三个插手点：`agent/inbox/claimed`（记住本轮文本）· 段 provider（现算）· 调度那一小块（§7.4） |

**它不做什么**：不解析模块内部结构（模块只给动作与回执）· 不改 DSH 的包 · 不接管会话与循环。

## 13.3 与 DSH 的关系（本次的形态决定）

**借用 DSH 的库与服务，不按它的 profile 组装方式改它**：

| 借 | 自己写 |
|---|---|
| `dsh-llm`（模型调用）· `dsh-session`（会话与日志）· `dsh-tools`（工具注册与分发）· `dsh-agent-loop`（循环）· `dsh-system-prompt`（提示词注册表）· `dsh-web-app`（界面） | **本层的全部**：预设 · 工具表 · 世界书引用 · 路由 · 提示词装配 · 界面上的那张表 |

**理由**：DSH 的装配（profile + patch 层）是为"改它自己"设计的；我们要的是**在自己的装配代码里把数据摆出来**。**"不封"因此是我们这层的性质，不是在别人的钩子上做的妥协。**

# 十四、验证

| 组 | 判据 |
|---|---|
| 请求表 | 加一行请求，界面与路由表同时看得到；删除后无残留 |
| API 池 | 多套并存；每条可独立指定；凭据不在池里；改配置下一请求生效 |

| R7 | 模块层的动作与工具表的映射是手写的 | 模块改了动作，工具表可能漏 | 默认那份**算出来**，不手抄（现在是 74 条） |

## 16.2 两条机制的实测（2026-10-10，本机 DSH 发行包）

§5.5 的 **P1** 与 **P2** 是"几个已验事实拼起来"才成立的，所以注册一个 `section()` provider + 一个 `agent/inbox/claimed` 监听，真跑了一轮确认：

```
[SEQ 1] agent/inbox/claimed   本轮批次在这里被领走  ← P2
[SEQ 2] 段 provider           组装时被同步调用      ← P1
        · 此刻本步的用户消息还没进会话（deriveMessages() 里看不见它）
        · 此刻 agent.session 可读，段 provider 拿得到 agent
```

跑法：`dsh-headless` + 一个临时 profile（`DSH_HOME` 指到临时目录，不动本机 web profile），任务文本 `只回一句话：第一轮。`。
实测到的组装次序（段名，18 段 / 24 工具）：

```
harness:identity · deployment:persona-prefix · plan:policy · tool:pwsh · tool:read · tool:write ·
tool:edit · tool:glob · tool:grep · tool:jobs · tool:web_search · tool:web_fetch · tool:goal ·
tool:workflow · tool:subagent · mcp-resource-servers · <order 5100 的段> · deployment:persona-suffix
```

**两条都对得上**，所以 §七/§八/§十 的结构一个字不用动，世界书命中的扫描文本取**本轮批次**（`agent/inbox/claimed` 给的那几条），不取历史。

## 16.3 一次真机联调（2026-10-10，DSH 0.2.0-rc.2）

拿默认那份真跑，看到回执：

**这串数字是模型通过对接层调用 `标签` 模块的 `status` 动作拿到的**，不是模型编的——
它与 `node test/run.js` 里"主库 52246 条 · 索引 51446 条"是同一份库的两个时点（索引那一项随后又变了几个）。

同一轮里还确认了三件事：

| # | 确认了什么 | 怎么确认的 |
|---|---|---|
| 1 | 身份与流程真的进了系统提示词 | 不带工具的问句，模型回"第一轮收到，工具箱在位"——那两句只出现在默认预设里 |
| 2 | 工具真的登记进了模型能看见的那份 | 模型在没被告知工具名以外的信息时，直接调了 `tag_status` |
| 3 | 装配层递进去的位置是对的 | 回执里的 52246 条来自 `程序/内置资源/标签/` 初始化的个人库，与配置里的 `项目根` 对得上 |

**踩到的两个坑记在上面决定 43 与 44**：工具名必须 ASCII；插件不能自带 DSH 的包（两份副本会让 `Symbol()` 对不上）。

| 45 | **对接层的 `node_modules` 由它自己装**（`pnpm install`），profile 不再重复装 DSH 的包 | 同上一条的另一种形态：只要同一个 profile 里出现两份 `@deepseek-ai/*`，symbol 与单例就会错位。所有 DSH 的包只从 DSH 安装处解析一处 |

| 47 | **切分只有一份，由装配层把装订模块的那一份递给翻译模块** | 切分是"这段文本长什么样"的判断，两条路必须得出同一结果（规则 7：必须保持一致的清单不该存在）。模块之间不互相 `require`（§七 规则 1 的同源） |

| 49 | **本地模型的推理依赖装在对接层**（`onnxruntime-node` / `sharp` / `@huggingface/transformers`） | 模块目录保持"无依赖、纯逻辑"，与另外七个模块同形；模型目录由配置给一格，与地址 / 凭据同一处 |
| 50 | **`harness:source`(10000) 由宿主自己装，我们不注册也不去关** | 它是 DSH 的 bin 在启动时装的那一段（`HARNESS_SOURCE_SECTION = "harness:source"`）。决定 38 因此在本层是"不注册 9000 / 10100、也不动 10000"，没有代码要加 |
| 51 | **打包分两种：默认不含模型，`-IncludeModels` 才含** | 本轮定了流程：平时检查迭代的包几十 MB，发出去的那份才带模型（约 1.5 GB）。打包脚本只打包、不删任何东西 |

## V1.5.1 独立界面装配（决定 52）

DSH 插件的装配方式不变。双击启动的独立界面由 `程序/会话模块/index.js` 管理本机会话，`程序/对接层/会话执行.js` 提供执行端口，借已有 `服务商.请求` 发送 OpenAI Chat Completions 报文，复用 `登记工具` 的参数、说明、执行与回执。每轮读取主 AI 的模型工具设置，世界书 `执行({请求:主AI,文本})` 使用同一请求订阅列表。世界书前后进入系统消息，按深度紧贴输入之前，工具定义单独进 tools。模型自己决定调用和结束，界面提供停止，不预设调用流程与次数上限。

独立识图与翻译请求经宿主把请求名装配为预设里的链路标识、模型名及世界书正文，再交服务商；链路未指定用 API 表第一条，指定但不存在明确失败。副请求不自动继承主 AI 的身份与流程。独立会话与 DSH 会话不互相迁移，不查桥也不作回退。

独立宿主只造一份图片、主 AI 与会话门面；会话 describe 加入交付面，默认主 AI 工具仍只从七个业务模块生成。DSH apply 不装会话文件适配器。工具登记显式注入输出格式化函数：DSH 用 `编码JSON回执`，独立执行器把图像字节保存到本轮会话并交出严格的 session-image 标记。取消通过第三运行上下文传到 ComfyUI，业务参数不带 signal。

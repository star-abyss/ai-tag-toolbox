# 性能分析与优化方案 V1.4.200

日期：2026-09-07。数据和代码基准为当前 V1.4.200 工作区，测试在同一台 Windows 机器上使用 Node 24.19.0 运行。下面的时间是单次冷加载测量，用于定位瓶颈，不是跨机器性能承诺。

## 当前测量

| 阶段 | 当前耗时 |
| --- | ---: |
| `createTags` 读取、解析和建立标签索引 | 约 148.5 ms |
| 创建角色模块对象 | 约 0.1 ms |
| 角色库首次完整加载和建立 34,122 条索引 | 约 155.3 ms |
| 角色库首次空查询分页 | 约 19.4 ms |
| 角色库首次中文搜索 | 约 33.4 ms |
| 角色详情展开 | 约 0.3 ms |

主要数据体积：角色表约 10.7 MB，词库同义词约 1.46 MB，识图模型词表约 0.55 MB，新增通用词约 26 KB。角色计数已改为只读取约 1 KB 的 manifest，不会触发角色全文加载。

## 已确认的根因

### 1. 首次进入角色库会阻塞渲染线程

`src/modules/characters.js` 的 `load()` 使用同步 `readFileSync + JSON.parse` 读取整个 `characters.json`，随后构造 34,122 条对象、名称索引、作品索引，并调用 `tags.list()` 复制角色名资料。首次进入角色页时，这段工作发生在 UI 事件调用栈内，所以窗口会短暂停顿。

### 2. 普通 Tag 搜索仍是全表扫描

`src/modules/tags.js` 的 `searchIds()` 每次查询都会遍历约 19,692 个标签。宽松搜索第一次使用时还会为每个候选建立分类、关键词和紧凑索引。输入框虽有 120 ms 防抖，但一次搜索本身仍然是同步计算。

### 3. 搜索结果会重建较多 DOM

`src/app-view.js` 的搜索回调会同时重绘侧栏分类、结果区和最多 400 个 Tag 芯片。用户连续输入时，旧的计时器会取消，但已经开始的同步扫描和 DOM 重绘无法被中断。

### 4. 翻译和角色搜索会重复生成对象

翻译参考会从当前标签模块建立完整 catalog；角色详情每次打开都会把关联 Tag 映射成公开对象。单次详情很快，重复打开和快速切换时会产生不必要的短生命周期对象。

## 优化原则

- 先把阻塞主线程的工作移出首帧，再优化算法；不改变搜索排序、成人过滤、角色引用和现有用户数据格式。
- 常规 Tag 和角色资料使用独立索引；隐藏角色专用词继续不进入普通搜索。
- 所有异步加载都要有 loading、error、retry 状态，不能用空结果掩盖加载失败。
- 先用同一组性能基准证明收益，再进入下一阶段，避免同时改变数据格式和 UI 行为。

## 推荐实施顺序

### 阶段 A：低风险索引和渲染减负

目标是减少每次搜索的同步工作，不改变对外接口。

1. 在构建阶段生成 `tag-search-index.json`，为每个普通 Tag 保存规范化英文、中文、别名、分类和 ID；启动时直接读取紧凑索引，避免宽松搜索首次逐行建立字段。
2. 在 `tags.js` 增加 `characterNameIndex()`，只返回角色 ID、中文名、别名和成人标记。角色模块不再通过 `tags.list()` 克隆完整 Tag 对象。
3. 将 `searchIds()` 的结果缓存键扩展为输入、精度、分类、子分类和成人状态；相同查询直接复用 ID 数组。
4. 搜索输入使用 `requestAnimationFrame` 合并同一帧更新，只有查询真正变化时重绘结果；分类数量和侧栏 DOM 在查询变化时不重复生成。
5. 保留现有 400 条显示上限，先采用稳定的结果节点复用。只有性能基准仍不足时，再考虑虚拟列表。

预期收益：普通搜索的首次宽松查询不再承担索引构建，重复查询主要变为缓存读取；搜索输入期间的 DOM 更新次数减少。该阶段风险最低，适合先实现和发布一个内部迭代版本。

### 阶段 B：角色库异步加载

目标是让首次进入角色页先显示页面和骨架状态，再在后台完成资料索引。

1. 将 `characters.js` 的同步 `load()` 拆成 `ensureLoaded()` Promise；使用 `fs.promises.readFile` 读取 JSON，解析和索引建立放到异步任务中。
2. `page()`、`get()`、`series()`、`select()` 改为返回 Promise；`primary-tools` 已经是异步 handler，AI 接口可以直接等待；角色视图在加载期间显示稳定的 skeleton。
3. 角色库第一次打开后，在空闲时间预热名称和作品索引；应用首屏只调用 `count()`，不预热 10.7 MB 资料。
4. 每次查询使用请求序号或 AbortController 丢弃过期结果，防止用户快速切换作品或关键词时旧结果覆盖新结果。
5. 保留当前 `characters.count()` 的同步轻量接口，侧栏计数和首屏不需要等待角色资料。

预期收益：首次点击角色库时主线程不再被 155 ms 的同步加载占住；用户先看到角色页，再等待结果出现。风险是接口从同步变为异步，必须一次性更新 UI、AI 和测试调用方，不能只改其中一层。

### 阶段 C：角色数据分片

只有阶段 B 在低端机器上仍不足时才做。构建阶段生成：

```text
characters-index.json       # id、英文名、中文名、别名、作品、count
characters-profiles-00.json # 按 ID 首字符或作品分片的特征引用
specific-tags.json
manifest.json
```

列表和作品筛选只读取 index；打开详情时才读取对应 profile 分片。分片键必须由构建脚本固定生成，并在 manifest 中列出版本和校验值。不能按用户任意输入拼接文件路径，避免路径穿越和缓存失效。

预期收益：首次角色搜索只解析较小的 index；详情按需读取。代价是构建、更新、缓存和迁移复杂度上升，应该等异步加载证明不够后再采用。

### 阶段 D：性能基准和回归门槛

增加 `scripts/perf-characters.cjs`，只在开发或 CI 中运行，不在用户启动流程执行。记录：

- Tag 冷加载、角色 manifest 读取、角色首次加载、空查询、中文搜索、作品筛选、详情展开。
- 10 次连续搜索的中位数和 P95。
- 搜索期间结果 DOM 节点数和每次输入触发的重绘次数。
- 异步请求过期结果被丢弃的次数。

阶段 B 之后建议以同一机器的相对指标验收：角色页面首个可交互状态不等待完整角色 JSON；连续搜索不出现旧结果覆盖新结果；P95 不得比基准增加。具体毫秒阈值在采集两台低端机器数据后再定，不先写死一个脱离环境的数字。

## 暂不采用的方案

- 不把 34,122 条角色资料再复制到普通 Tag 文件，会增加启动和搜索内存，并重新引入隐藏词污染。
- 不在渲染进程中每次输入启动子进程或重新读取 JSON，这会把磁盘和进程开销叠加到搜索延迟。
- 不直接把列表限制到几十条来掩盖全表扫描；用户仍需要完整角色库和作品筛选。
- 不先上复杂数据库或全文检索依赖。当前规模用构建期紧凑索引和异步加载即可验证收益。

## 当前结论

本轮已完成角色计数的轻量读取，降低了侧栏刷新带来的额外成本。主要卡顿仍来自角色首次同步加载、普通 Tag 全表扫描和结果区批量 DOM 重绘。下一步优先实施阶段 A，再用基准决定是否进入阶段 B；阶段 C 只作为数据规模继续增长后的方案。

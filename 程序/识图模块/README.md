## 一、它是什么 / 它不是什么

**一张图进来，要么本地模型给它打标，要么把图里藏着的提示词读出来，要么交给模型看。**

| 它做 | 它不做 |
|---|---|
| 本地打标：图 → 一批标签（过阈值、配中文名） | **不拥有模型**：模型与推理引擎由装配层递进来 |
| 读元数据：PNG 文字块中的提示词 / 工作流；识别 ComfyUI `prompt` API graph 与 `workflow` 节点图里的正负提示词 | **不解析 EXIF**（要另一个解析器，等有需要） |
| 看图：图 + 提示 + 参考标签 → 标签与描述 | **不认识 AI 链路**：发请求、选模型、密钥都归装配层 |
| 把字节交给打标引擎 | **不找路径、不读盘、不认别的模块** |
| —— | **不编译图、不做缩放**（那是引擎那一层的活） |

**位图从哪来不是它的事**：它只交出一个「引用」，由装配层去图片模块取字节。

## 三、三条路

```
① 读元数据   PNG 文字块 → 提示词 / 负向 / 工作流 / 参数     不要模型，最快
② 认图      图 → 本地模型打标 → 标签（+ 中文名）            离线可用，要 1.25 GB 模型
③ 看图      图 + 提示 + 参考标签 → 模型给的标签与描述        要一条能看图的链路
```

**三条可以串起来用**：先 `读元数据`（AI 画的图往往直接就告诉你提示词了），不够再 `认图`，还不满意再带上参考标签走 `看图`。

## 四、怎么调

```js
识图.run('看模型');                                    // 这一格备齐了没有
await 识图.run('读元数据', { 存放地: 'gallery', 条目ID });      // 图里藏着的提示词
await 识图.run('读元数据', { 字节: pngBytes });             // 直接解析原始 PNG 字节，不走存放地
await 识图.run('认图', { 存放地: 'gallery', 条目ID, 阈值: 0.6, 上限: 20 });
await 识图.run('看图', { 存放地: 'gallery', 条目ID, 提示: '这是什么风格', 参考标签: ['1girl'] });

await 识图.标签({ 存放地: 'gallery', 条目ID });            // 只要标签数组；失败给 []
```

引用参数是**扁平的**：`存放地`（session / gallery / vision）· `条目ID`（`img_…`）· `会话ID`（只在 session 时给）。`读元数据` 也可直接收 `字节`；给了字节就由同一元数据解析器读取，不需要先存图。模块内部把引用收成 `{ 作用域, 条目ID }`，再交给 `取图字节`。

## 五、怎么接进装配层

```js
// 对接层/index.js 里那一段
const 识图 = 要(path.resolve(项目根, '识图模块/index.js')).createVisionModule({
  取图字节: (引用) => {
    const 回 = 门面.image.run('取内容', { 引用 });
    return 回 && 回.ok ? 回.data : null;
  },
  查词: (词们) => 门面.tag.recognize(词们),
  tagger: 引擎.打标,                 // 对接层/模型引擎/识图.js
  读元数据: 读PNG元数据,
  看图: 造看图({ 调度, 请求名: '识图', 提示词 }),
  引擎: { id: 引擎.id, 名字: 引擎.名字, 阈值: 引擎.阈值 },
});
```

**位置从不进模块**：模型目录住配置里，装配层读进来、把装好的引擎递进去。

## 六、哪条不能动

1. **不许把文件路径 / 地址放进对外参数。** `读元数据.字节` 可接 PNG 原始字节；其它引用参数是标识。
2. **不许自己找模型、自己读盘。** 位图走 `取图字节`，模型走 `tagger`。
3. **核心不许 `require fs` / `path`**，也不许 `require` 别的模块。
4. **查词抛错不许带崩整件事**：中文名给 `null`，标签照给。
5. **出口冻住**，不递 `core` / `port` / 适配器。
6. **失败一律 `{ ok:false, reason, code }`**，不抛错（装配阶段除外）。
7. **不做兼容层、不留回退开关。**

## 七、依赖从哪来

| 依赖 | 递不进来会怎样 |
|---|---|
| `取图字节` | **构造即抛错**（装配阶段允许抛） |
| `tagger` | `认图` 报 `VISION_NO_ENGINE`；另两条路照常 |
| `看图` | `看图` 报 `VISION_NO_VIEWER` |
| `读元数据` | `读元数据` 报 `VISION_BAD_METADATA` |
| `查词` | 中文名一律 `null` |

**模块自己不找、不猜、不探测路径。** 多级兜底（`a || b || c`）是缺陷。

## 八、改完怎么验

```bash
node test/run.js          # 41 条
node test/run.js 认图      # 只跑名字里含"认图"的
npm test
```

**自检查什么**：四条路各走一遍 · 阈值与上限 · 引用不对的几种形状 · 查词抛错不带崩 ·
元数据解析（含坏文件）· 端口清单与动作表 · 造图工具自己对不对。

**自检不查什么**：真模型打得准不准（那要真机跑，见 §九）。

## 九、这一版做到哪了 / 还差什么

**已实现**：四个动作 · 三条路 · 端口 + 两个适配器 · 43 条判据。

**真机实测**（`对接层/模型引擎/识图.js` + `模型/vision/wd-eva02`）：

| 项 | 结果 |
|---|---|
| 模型加载 | 1.9 秒（1.25 GB 的 ONNX，词表 16473 条） |
| 一次打标 | 0.9 秒 |
| 一张 64×64 假图 @ 阈值 0.6 | `no_humans 90.1% · explicit 76.3% · general 75.0% · pixel_art 72.4%` |
| 装进 DSH 真机跑（经 DeepSeek 那一轮的模型调用） | 一张 512×512 的 PNG：`no_humans 93.6%(无人) · general 92.8%(一般) · pixel_art 86.6%(像素画) · pastel_colors 85.5%(粉彩配色) · colorful 61.8%(五彩缤纷)`；同一张图的元数据读出 `a cat, sitting` / 负向 `blurry` / 尺寸 512×512 |

**已知的缺口**：

| 项 | 状态 |
|---|---|
| EXIF | 不解析（只认 PNG 的文字块） |
| 「哪些操作对模型可见」 | 归门面层；四个动作全交出去 |

# 标签模块设计

> 本模块维护 tag 与组的数据、它们的位置与用户改动，对外提供检索。
> 只写本模块提供什么。别人怎么用它，不在这里写。
>
> **只认本仓库的代码**：本项目是重写，旧目录（`工具箱\`）里的实现不作参考。
> 怎么调 → [对外接口.md](对外接口.md)；东西在哪 / 不能动什么 → [README.md](README.md)。
> 决定记录见本文末尾（§七）。

---

# 一、边界

**做什么**

维护 tag 与组两类记录、它们的分类与收藏位置、用户改动与注释，并对外提供检索。

**不做什么**

| 不做 | 归谁 |
|---|---|
| 把一段文本拆成词列表 | 认识那个格式的模块；本模块**只收单个词** |
| 归一化的实现 | 共用的纯函数，本模块**依赖它，不拥有它** |
| **自动收词** | 查不到就是**没有收录**；要加，用户**自己手动加**。**系统不自动加** |
| 解析库外数据的结构 | 产生它的那个模块 |
| 数据落盘 | 存储 |
| 界面、入口、提示 | 装配层与界面层 |

# 二、数据

## 2.1 记录

```
tag = { ID, tag 本身, 中文名 }
组  = { ID, 组名（= tag 本身）, 中文名, 成员 ID }
```

| 字段 | 形状 | 说明 |
|---|---|---|
| **ID** | 整数或字符串 | **永久不变 · 不复用**。自建库的带 `u` 前缀，见 2.2 |
| **tag 本身 / 组名** | 逗号分隔的字符串 | 小写 + 下划线；**第一个是规范写法** |
| **中文名** | 逗号分隔的字符串 | **第一个是主名，其余是别称** |
| **成员 ID** | ID 的列表 | **只有组有**。成员只存 ID |

**组 = tag + 成员 ID。** 就这一处差别。除成员 ID 外，对 tag 的一切操作对组同样成立。

**记录上没有"是不是组"的标记**——由角色表回答。

> **作品是 tag，不是组**（决定 120）：那 4049 条作品**没有 `成员` 字段**，所以它不在任何"组"的名单里。
> 它和角色的两条关系、页与类怎么摆、未分类怎么算，见下一节 2.1.1；出词顺序见 [渲染顺序.md](渲染顺序.md)。

**取值约定**：多个中文名是**同一个 tag 的多个写法**，不是多个 tag。搜其中任意一个，都出这一条记录。
显示时取第一个为主名，其余作别称。

### 2.1.1 角色与作品（决定 120–124）

**库里三样东西。**

| 东西 | 是什么 | 形状 | 谁在它的成员里 |
|---|---|---|---|
| **作品** | 普通 tag | `{ID, 名称, 中文名}` —— **没有 `成员` 字段** | 没有。它不当组 |
| **角色** | 组 | `{ID, 名称, 中文名, 成员}` | 第 0 位 = 作品 tag；其余 = 特征 tag |
| **普通词** | tag，不是组 | 同作品 | 没有 |

**成员里只有两种东西**：一条作品 tag + 若干特征 tag。**没有组。**

**两条关系各一个家，都不碰"组不许嵌组"（决定 91）。**

```
反向：作品 → 它有哪些角色     走类
      页「角色组」→ 类「touhou」→ 成员 [9540, 9541, …]
      ← 靠"类是分类的依据"回答，不读角色的成员，所以没有嵌套

正向：角色 → 它在哪个作品     走成员第 0 位
      角色 9540 的成员[0] = 19047「touhou」
      ← 第 0 位是 tag（不是组），所以角色组里装的仍然不是组
```

**作品集**是 `表/系列.json` 那 4049 个 ID（源数据给的，只读）。**"是不是作品"由它回答**，
不由"是不是组"推 —— 作品退回 tag 之后，它不再带成员，`record.groups` 与 `identity.isRole` 都答不了这件事。

**唯一一条要守的单向性**：**作品 tag 不许出现在任何类的成员里**（它是"类名"那一侧的）。
类成员只装两种东西：角色（页「角色组」底下）与普通 tag（别的页底下）。

**未分类**：成员第 0 位**不在作品集里**（空成员也算）的角色，落在页「角色组」底下的类「未分类」。
**不许按"第 0 位是什么"硬分配** —— 实测有 9 条角色的首位是 `1girl`、`medium_breasts`，硬分配会建出一个叫「1girl」的作品类。

**页面上的样子**：

```
页「作品」    └ 类「作品」       成员 = 全部作品 tag        ← 作品是"词"
页「角色组」  ├ 类「touhou」     成员 = 311 个角色           ← 作品是"类名"
              ├ 类「vocaloid」   …
              ├ …（4049 个）
              └ 类「未分类」     成员 = 没有作品的角色（526 个）
```

搜作品时**两种候选并列**：那条 tag（能选进提示词）与那个类（点开 = 它的成员）。
出词顺序见 [渲染顺序.md](渲染顺序.md)（一份页序 + 两张表）。

## 2.2 库与 ID

**记录住在库里，一共四个库。**

```
主库      原有记录（来自源数据）        ID：数字，自增
自建库    用户自己新建的记录            ID：u + 数字，自增
隐藏库    被隐藏的记录（剪进来的）      与来源库同形
修改库    被改过的记录的【原文】        与来源库同形
```

| 规则 | |
|---|---|
| **两套 ID 空间** | 主库 `1, 2, 3…` · 自建库 `u1, u2, u3…`。**看一眼 ID 就知道它从哪来** |
| **两个计数器** | 每个库一个，**随库同一次原子写**落盘，**只增不减，永不看库里的最大值** |
| **ID 永不变 · 不复用（不补位）** | 隐藏、改名、删记录都不释放号码 |
| **引用带前缀** | 组成员、类成员、"取一条"，拿到的 ID 自己就知道去哪个库找 |
| **没有迁移** | 改了 ID 就是全断 |
| **源数据本来没有 ID 的**（例如外部导入的角色表） | 在清洗时按名字分配一次；之后 ID 跟着那份源数据走 |
| **"改名"指的是什么** | 改 `tag 本身`。**ID 不动，名字可以改，显示名不是 ID 的载体** |

**为什么自建要单独一个库**：`能不能删` 一眼就有答案（自建库里的 = 用户自己的，能删；主库里的 = 原有的，只能隐藏），
**因此不需要"创建表"**；ID 前缀又保证了两个库的引用永不撞。

**本模块占的键**（这一层是模块"往哪个格里放"的约定，位置仍由装配层递进来）

```
主库  自建库  隐藏库  修改库              一个库一处；主库按 ID 分片
成人  角色                                两张身份表
注释  常用词                              一条记录一条 / 一份常量
分类字典  分类.<页ID>.<类ID>               一格一个类
收藏字典  收藏.<页ID>.<类ID>               同形，只是根不同
```

**位置的两层都是键**：字典一个键，**每一个类单独一个键**（不是"一个大格里套数组"）。
好处是改一个类不碰任何别的类 —— 这正是存储那条「写一格不影响别的格」。

**记录也照这个道理分片**（决定 107）：一个库不装成一个数组，而是**按 ID 切成若干片**，
一片 1000 条。**片号由 ID 算出来**（`floor(ID ÷ 1000)`），跟记录在数组里的位置无关 ——
所以删一条记录**不会让后面的记录换片**，改一条只重写它自己那一片。

| | 一个类 | 一条记录 | 一张表 |
|---|---|---|---|
| 切法 | 一格一个键 | 一片 1000 条 | 一张表一处 |
| 改一个要写 | 160 字节 | 约 100 KB | 整张表（本来就小） |

## 2.3 表

**除记录以外的一切都是表。**

> **总判据：一处字段值只存一处。**
> 凡是"同一份数据要在两个地方各存一份"的表，都不存在——不一致就是这么来的。

**记录上不留归属**：一条记录属于哪个类，只由「页 → 类 → 成员 ID → 记录」推出来。
记录上曾经有个 `子分类` 字段（指向旧子分类的哈希），那是重构时的中间变量，
既是第二份归属、运行时又没人读 —— **已按总判据丢掉**（决定 108）。

### A 类 —— 身份

| 表 | 装什么 | 回答什么问题 |
|---|---|---|
| **成人标签表** | 哪些 ID 是成人标签 / 组 | 这条要不要挡住 |
| **角色表** | 哪些 ID 是角色组的 ID | 哪些组是角色组 |
| **系列表** | 哪些 ID 是系列组的 ID | 哪些组是系列组 |

**"是不是"就只是"表里有没有这个 ID"。**

**"是不是组"也由表回答**：带成员的那条记录就是组；在角色表里 = 角色组；在系列表里 = 系列组。
**我们不发任何组**，所以两张表就够，不需要另设"用户组表"。

**这三张表由源数据覆盖**——它们不是用户数据，是"哪些 ID 属于哪一类"的索引。
用户自建的组不在任何一张表里，所以自建的组既不是角色组也不是系列组。

**两张组表各落一个文件**：`表/角色.json`（角色组，实测 34120 个）· `表/系列.json`（系列组，实测 4049 个）。
存量库原先只有一份 `表/角色.json`，里面装的其实是系列组 —— 两个文件的来历见决定 118。

**收藏不在这类**——它由位置回答（见 B 类）。

### B 类 —— 位置

**分类与收藏是同一套结构的两份数据。** 结构只有一个：**字典 + 一层内容格**。

```
分类  →  分类字典 { 计数器, 页列表 }
         分类/<页ID>/<类ID>      一格一个类

收藏  →  收藏字典 { 计数器, 页列表 }
         收藏/<页ID>/<类ID>      一格一个类
```

**字典装什么**（只有 ID、顺序、名字、配色——不装成员）

```
分类字典 = { 计数器, 页列表 }

页 = { ID, 页名, 配色, 类 ID 列表 }
类 = { ID, 类名, 配色 }              ← 页列表里每页一条，类挨着页排
```

**内容格装什么**（只有 ID 与顺序）

```
分类/<页ID>/<类ID>  =  [ tag / 组 ID, … ]
```

| 规则 | |
|---|---|
| **一格一个类** | 写一个类不碰任何别的类。不用"一个格装下整个分类体系" |
| **格里只有 ID 和顺序** | 真正的数据在库里那一条记录上 |
| **类格里不得有反向表** | 不存"这个 tag 属于哪些类"——有了它就有两份数据要对齐 |
| **归属不另存字段** | 归属 = 页 → 类 → 成员 ID → 记录，读出来的 |
| **位置不参与加载** | 它本来就在格里，不需要"再改一下状态"这一步 |
| **悬空与重复** | 指向不存在记录的 ID **跳过不渲染**；同一个 ID 出现两次**都留着**，不做去重 |
| **页名 / 类名可以重名** | 标识是 ID，名字只是显示 |
| **删页带走子类** | 删页 = 删字典那条 + 它底下所有类格；删类 = 删字典那条 + 那个格 |
| **配色** | 就是两个颜色值（底色 + 文字色），没有别的形状 |

### C 类 —— 内容

| 表 | 装什么 |
|---|---|
| **注释表** | 注释文本 + 对应的 tag / 组 ID |
| **常用词表** | 常用的一批词 |

| 规则 | |
|---|---|
| **注释一条记录一条** | 空注释 = 删除。悬停时读取；**不参与检索**；删记录时连带删，**漏了也不补**（渲染时匹配不到就跳过）。**一条记录一条注释**这句话只管"一条记录上挂几份"，不管同一条注释文本能不能出现在两条记录上 |
| **常用词表是常量** | 从常见的标签榜里收一批，**做成数据、不做维护入口**。它只影响"同档内谁排前面" |

**隐藏与修改都不是"表"，是两个库**——见 2.2 与 2.6。

### 搜索用的表

| 表 | 键 | 用途 |
|---|---|---|
| **等值表** | 比对键 | 全等（第 1 档），O(1) |
| **连写表** | 连写键（去掉分隔符） | 连写相等（第 4 档），O(1) |
| **切词表** | 按 `_` 切开的段 | 切词命中（第 2 / 3 档），O(1) |
| （兜底档不建表） | —— | 包含命中在第 5 档扫一遍记录 |

**可以从记录重建**——不承担正确性，只承担快慢。
**只为检索的两处建**（`tag 本身` 与 `中文名`），**位置、注释、常用词都不进检索**。

> **曾经有过一张前缀表**（首字符 → 记录），是为原 13 档的前缀分层做 O(1) 加速的。
> 分档收成 5 档之后（决定 104）**它没有使用者了，已删** ——
> 前缀命中退到兜底档扫一遍，实测热查询 4–14ms（5 万条记录），够用。

## 2.4 加载顺序

```
① 读主库 / 自建库      →  这就是有效值，没有第二层要替换
② 读身份表（成人 · 角色）
③ 读位置（按需）       →  页、类、成员 ID
④ 搜索用的表按需重建    →  第一次查询时才建，数据一变打脏标记
```

**库就是有效值。** 隐藏的和被改的原文都不在这里——它们在隐藏库与修改库里，**不参与加载**。

**成员 ID 悬空的处理**：组里存了成员 ID，而那条记录不存在（被删或被隐藏）——
**不剔除、不改组的数据**，只在组装输出时**跳过**指向空处的成员（见 3.4）。

## 2.5 重建

**重建 = 主库 + 它的计数器重置，仅此一项。**

```
主库   ← 新源数据
计数器 ← 归零重排
自建库 · 隐藏库 · 修改库  ← 不动（u 前缀天然隔离，撞不上）
```

**重建就是重来**：旧 ID 一律不沿用，旧引用一律不做迁移。**恢复和还原不跨重建**。

## 2.6 隐藏库与修改库

**两个库都是"记录的去处"，不是"状态的标记"。**

| | 怎么进去 | 装什么 | 怎么出来 |
|---|---|---|---|
| **隐藏库** | **剪切**：记录从来源库移出，整条进隐藏库 | 那条记录本身 | **恢复** = 按 ID 前缀扔回来源库 |
| **修改库** | **复制**：把【改之前】的原文抄一份进去，然后直接改来源库 | 改之前那一条 | **还原默认** = 按 ID 覆盖来源库，然后删掉这一份 |

| 规则 | |
|---|---|
| **隐藏 = 扔进去 = 任何方式都查不到** | 查库、认词、取一条，全都不返回它 |
| **修改 = 直接改库** | 改一处，全部相关的地方一起变（因为位置那边只有一个 ID） |
| **每条 ID 只抄一次原文** | 改第二遍时，修改库里已经有这份 ID 了，**直接改库，不再覆盖原文** |
| **还原用一次就销** | 还原之后把修改库那条删掉；再改一次会重新抄一份 |
| **删记录连带删** | 删掉一条记录，把修改库里那份也删掉 |
| **两个库都是混合的** | 主库和自建库的记录都可能进去，**靠 ID 前缀分辨它从哪来** |
| **只被两个地方读** | 它们自己的界面、和写入。**检索、认词、渲染一概不许碰** |

# 三、对外能力

**这个模块是个六边形：外面那一圈只认一套动作表，里面那一层不认识存储。**

```
界面 ──▶ 门面：run(动作, 参数) · actions · describe() · 两个查询入口
功能 ──▶        │ 只认这套
                ▼
            核心：不认识盘、不认识文件
                │ 端口：read / set / remove / list / scan / status
        ┌───────┴───────┐
   文件适配器        内存适配器
```

| # | 规矩 | 为什么 |
|---|---|---|
| 1 | **对外不管功能还是界面，都走同一套动作表** | 界面不认识核心，也不 require 核心里的任何文件 |
| 2 | **面子上不递内部件** | 没有 `store` / `library` / `search` 这样的口子；要什么能力就加动作 |
| 3 | **核心不认识存储** | 换适配器，核心一行不改；测试用内存端口跑，这件事就被证明 |
| 4 | **每个动作的输入输出都写在定义里**，`describe()` 能整张表交出去 | 界面照着它画该有的东西，不另写一份清单（规则 7） |
| 5 | **三态读是端口的硬要求** | 确实没有 与 读不懂 混成一个，就会出现"坏文件被当空、下一次写清光" |

## 3.1 检索

**回答一个问题：库里有没有这个写法。**

检索是本模块的**子能力**，对外没有独立接口，仍由本模块那一份清单交出。

### 3.1.1 两个入口

| 入口 | 输入 | 输出 | 需要什么 |
|---|---|---|---|
| **查库** | **一个**查询串 | 最多 30 条记录（排序好）+ 有没有更多 | 等值表 · 连写表 · 切词表 |
| **认词** | **一批**词 | 每个词一条：**中文名** 或 `null` | 查表 |

**查什么**：查两处——**① `tag 本身` ② `中文名`**。两处都在 2.1 的同一张记录上。
命中任意一处，都返回**那一条记录**。

**查哪个库**：查库与认词都**同时查主库和自建库**。隐藏库、修改库**不查**。

**共用**：数据来源（同一份记录）· 归一化（同一个前置）· 失效时机（数据变了，两边一起作废）。
**不共用**：取数方式（一次一个 / 一次一批）· 输出形态 · 排序。

### 3.1.2 查库的口径

```
查库(一个查询串)  →  最多 30 条记录 + 还有更多

① 归一化      用户输入 → 比对键（只产出比对键，不改真实文本）
② 分档        按下表给候选分档（5 档）
③ 排序        同档内比常用词 → 长度 → 主库优先 → ID
④ 截断        取前 30 条，多出来的用"还有更多"表示，不分页
⑤ 返回整条记录  不返回字符位置（位置是比对键上的，拿去高亮会对不齐）
```

**匹配分档**（序号越小越靠前）

| 档 | 条件 | 例（查 `miku`） |
|---|---|---|
| **1** | **全等**：与 `名称` 主值 / `中文名` 主值 / 任一别称 / 其余中文名完全相等 | `miku` 这条记录自己 |
| **2** | **切词命中，且命中的是第一个词** | `miku_day` |
| **3** | **切词命中，命中的是最后一个词或夹在中间** | `hatsune_miku`、`my_cat_ears` |
| **4** | **连写相等**：分隔符可以省（`fuhua` → `fu_hua`、`longhair` → `long_hair`） | `hatsunemiku` |
| **5** | **兜底**：名称或中文名里含这个串 —— 前缀、"词尾陷在词里"、包含都在这档 | `mikusa`、`catapult`、`bobcat` |

> **5 档取代了原来的 13 档**（见决定 104）。理由：13 个档位号里只有 10 个真能出现，
> 其中「整段相等」那一档与「名称主值全等」同条件、**永远轮不到**；「别称全等」那一档
> 被「连写相等」整档截胡。档位号是要交出去的（界面拿它标"精确命中"），
> **摆着到不了的档只会让人读错。**
>
> **切词那一层仍然按"命中的是第几个词"分先后**（决定 100 的判据没变）：词首 > 词尾 ≥ 词中。
> 只是从"四档"收成"两档"—— 词尾与词中同档，让位给同档内的常用词与长度。
>
> **前缀与"陷在词里"不再分档**（原 9/10）：判据是**词尾有没有吃进别的字**，
> `cat_ears` 的 `cat` 词尾吃界、`catapult` 的 `cat` 词尾陷在 `pult` 里。
> 但现在两者同落兜底档 —— 而且 `cat_ears` 早在第 2 档就被切词挑走了，
> 真正落兜底的只有 `catapult`、`bobcat` 这类。同档内靠常用词与长度分先后，**相对次序不变**。
>
> ⚠️ **同档内必须先比常用词、再比长度。** 反过来会把"名字短"当成"更相关"：
> 搜 `miku` 时 `hatsune_miku`（**常用词表第 0 名**）会被二十多条不出名的 `xxx_miku`
> 挤到二十名开外 —— 而那正是用户最常搜的那一个（决定 105）。
>
> ⚠️ **"把连写的词切开"这条我们试过，又拿掉了。** 做法是顺着字符走、
> 碰上库里真有的词就断开（`catgirl` → `cat` + `girl`）。实测结论：
> 带分隔符的 45,512 条记录里，**43,190 条靠连写键就够了**，剩下 2,322 条是
> `badfeet` 这种"自己去掉分隔符、而那个连写串库里也没有"的形式 —— 切出来的段
> 在库里**不是独立的词**（没有 `bad`、没有 `feet`），所以也切不出来。**收益 0，还老出 bug。**
> 结论：**不做拆分**（与"拆分不作为本模块的能力"一致）。要认一批词，走**认词**那一路。

**同档内**依次比：① **常用词表**里的优先 ② 命中字段值的**长度短者优先** ③ 主库优先 ④ ID 升序（结果稳定）。

**一个实词字符都没剩下的查询给零结果**：`;)` 归一化后是 `)`（`;` 折成下划线又被当首尾下划线剪掉），
而 `)` 是限定词括号的一部分、库里到处都是 —— 拿它去查会撞出一堆与用户意图无关的结果。
**有实词字符的照旧放行**：`:3` 归一化后是 `3`，而 `:3` 是库里真有的 tag（366 条）。

**不做**：不转义（逗号就是分隔符，按字段命中）；不做拼音、**错字容错**（写错一个字母、字母换位都不认）、打分模型、**连写拆词**。

**例子**

| 输入 | 结果 |
|---|---|
| `miku` | `miku_day`（词首，2 档）→ `hatsune_miku`（词尾，3 档）→ `aki_miku`（词尾，3 档，无常用词名次）→ `mikusa`、`mikudayo`（兜底，5 档） |
| `cat` | `cat`（全等，1 档）→ `cat_boy`（词首，2 档）→ `dos_cat`（词尾，3 档）→ `catapult`（兜底，5 档）→ `bobcat`（兜底，5 档） |
| `hatsune miku` | 归一化成 `hatsune_miku`，第 1 档直接命中 |
| `hatsunemiku` | 连写，第 4 档命中 |
| `fuhua` | 连写，第 4 档命中 `fu_hua` |
| `初音` | 兜底（5 档）—— 前缀不再单独分档 |
| `;)` | **零结果**（折完只剩 `)`，一个实词字符都没剩下） |
| （空） | 零结果。**不倒 30 条出来** |

### 3.1.3 认词的口径

```
查词(一个词)  →  中文名  或  null

① 查不到                  →  null
② 有多条匹配              →  取第一条（主库优先）
③ 查到词，但它没有中文名  →  null
④ 任何异常                →  null（不抛错）
```

**查不到就是没有收录**——这是结果本身，不是异常，也不是需要"决定收不收"的情况。
要加，用户自己在编辑界面加。**系统不自动加。**

**一个字都不许崩。结果可以不好，程序不能倒。**

由此**不需要"可信度"标记**——查到就是答案，查不到就是 `null`，没有中间状态。

**适用范围**：这是**认词这一档**的口径。别处若要"必须唯一才肯用"的严格口径（例如写进文件、给外部工具读），**那是另一个入口**。

### 3.1.4 归一化的位置

```
进检索 → 必须先归一化 → 再查
```

归一化是检索的**前置**，但**不归检索所有**：它是共用的纯函数，检索只是使用者之一。

**归一化只产出"比对键"，永不替换真实文本**：

```
用户输入的写法  ──归一化──→  比对键  ──→  查库
                              ↑ 用完就丢

用户输入的那段文本本身        一个字都不改
库里存的那条记录              一个字都不改
最终交出去的文本              一个字都不改
```

**归一化只做一件事**，匹配的强弱靠 3.1.2 那张分档表，不靠改归一化。
因此**查库不必分"严格档 / 宽松档"**——库和查询用同一个前置、产出同一种比对键，比一次就够。

## 3.2 取与改

| 能力 | 输入 | 说明 |
|---|---|---|
| **取一条** | ID | 给整条记录；隐藏库里的**取不到** |
| **改一条** | ID + 整条记录 | **直接改来源库**；第一次改之前把原文抄进修改库（见 2.6） |
| **新建** | 一条记录 | **只写自建库**，ID 由自建库的计数器自动分配 |
| **删除** | ID | **只能删自建库里的记录**；连带删掉修改库里那一份 |
| **隐藏** | ID | **任何 tag 与组都能隐藏**（含自建的）：整条剪进隐藏库 |
| **恢复** | ID | 从隐藏库读出来，按 ID 前缀扔回来源库。**是恢复这个动作的正式名字** |
| **还原默认** | ID | 用修改库里那份覆盖来源库，然后删掉修改库里那一份 |

**删除与隐藏的分工**

| | 谁能做 | 怎么做 |
|---|---|---|
| **删除** | 只有自建库里的（判据：它住在哪个库，**由 ID 前缀一眼看出**） | 直接删；**原有记录在任何时候都不允许删，只能隐藏** |
| **隐藏** | 任何 tag 与组 | **整条剪进隐藏库**，来源库里就没有它了 |

> 隐藏**不是**"从组里摘掉成员身份"——组的成员 ID 一个字都不动，那是另一件事。

## 3.3 位置

**页与类的增删改，是位置这一层的对外能力。**

| 能力 | 输入 | 说明 |
|---|---|---|
| **建页 / 建类** | 名字（+ 可选的配色） | ID 由字典的计数器分配，**页和类共用一个计数器** |
| **改页 / 改类** | ID + 名字 / 配色 | 键名不动，改的是字典里那一条 |
| **删页 / 删类** | ID | 删页**带走它底下的所有类**；删类只删那一个格 |
| **挂上** | 位置 ID + 成员 ID | 把 tag 或组放进一个类 |
| **卸下** | 位置 ID + 成员 ID | 把它从一个类里拿掉 |

**位置只管数据**：界面、拖拽、排序的手势是装配层与界面层的事，这里不写。

## 3.4 组装输出时的跳过

**一条规则，三个地方共用，不写第二份判断：**

```
拿一个 ID 去取记录  →  取不到（被删了或被隐藏了）  →  跳过，渲染下一个
```

用到的地方：**组的成员** · **页底下的类** · **类底下的成员**。

**数据一个字都不改**——悬空只是"读的时候跳过"，不是"写的时候清理"。

## 3.5 注释与常量表

| 能力 | 输入 | 说明 |
|---|---|---|
| **写注释** | 记录 ID + 文本 | 一条记录一条；**空文本 = 删除** |
| **读注释** | 记录 ID | 悬停时读；不参与检索 |
| **成人标签表 / 角色表** | —— | **由源数据覆盖**，本模块只读它、不写它 |

# 五、错误

**失败一律 `{ ok:false, reason, code }`。** 两个字段各管一件事：

| 字段 | 给谁 | 变了会怎样 |
|---|---|---|
| `reason` | 人、界面 | 改一句话只是文案变了，调用方不该跟着断 |
| `code` | 程序 | 调用方按它分支；加一个码就是加一个分支点 |

**码全部定义在 `error.js`**，门面用 `tags.ERR` 交出来。**`reason` 是"理由原文 → 码"那张表的键**——同一句原文在代码里只出现在一处，所以它可以直接当键，不必再造一个"理由编号"。

| 码 | 什么时候 |
|---|---|
| `TAG_NO_SUCH_ACTION` | 动作名不在动作表里（门面自己产） |
| `TAG_ACTION_FAILED` | 动作自己抛错；**或理由不在码表里**（门面自己产） |
| `TAG_RECORD_MISSING` · `TAG_NAME_REQUIRED` · `TAG_RECORD_READONLY` | 记录与名称：取不到 / 名空 / 删原有记录 |
| `TAG_NOT_HIDDEN` · `TAG_NOT_MODIFIED` · `TAG_ID_TAKEN` | 隐藏与修改：没藏过 / 没改过 / 还原撞号 |
| `TAG_PAGE_MISSING` · `TAG_CLASS_MISSING` · `TAG_PAGE_OR_CLASS_MISSING` · `TAG_CLASS_NOT_IN_PAGE` | 位置：页 / 类 对不上 |
| `TAG_PAGE_NAME_REQUIRED` · `TAG_CLASS_NAME_REQUIRED` · `TAG_BAD_POSITION_ROOT` · `TAG_NEED_ID_LIST` | 位置：参数形状不对 |

**落回 `TAG_ACTION_FAILED` 的是这三类**（有意不细分）：

1. 存储层报上来的 `权限` / `磁盘满` / `被占用` / `未知`
2. 坏键的 `读不懂`（该键被冻结，重试永远失败）
3. 任何没走到这里的抛错

**两条不算失败的**（有意如此，别去"修"）：

- `record.batch` 取不到的**静默跳过**
- `position.detach` 拿掉一个不存在的东西**算成功**，给回原样的表——和图片模块"删一个不存在的条目 = 未删除"是同一条规矩

**为什么失败也要给码**：调用方要能分支。**让调用方 `switch` 一句中文短语，等于把身份挂在名字上**——改一个字就断。§二 2.3 那条"一个东西的身份是它的 ID，不是它的名字"在这里同样成立。
